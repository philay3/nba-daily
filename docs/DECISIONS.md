# Decisions

Short entries: the decision, why, and the trade-off. Newest at the bottom of each section.

## Stack

### Next.js App Router + TypeScript + React for the web app
- Why: server components can query Postgres directly, so pages need no API layer; Chops already works in Next/TS.
- Trade-off: pages render per request (`dynamic = "force-dynamic"`) so `next build` never needs a database. Each visit hits Postgres; fine at this traffic, and data only changes once a day.

### Drizzle ORM + drizzle-kit, not Prisma
- Why: the schema lives in one TypeScript file (`web/src/db/schema.ts`) and drizzle-kit generates plain SQL migrations (`web/drizzle/*.sql`) that the Python pipeline can read and apply. Prisma's engines download from binaries.prisma.sh, which the build sandbox could not reach, and its generated client adds a binary to every deploy.
- Trade-off: fewer guard rails than Prisma (no generated client with relation helpers); queries are written with the Drizzle query builder or `sql` templates.

### snake_case everywhere (SQL columns, Drizzle keys, Python, JSON)
- Why: one vocabulary across the pipeline, the database, the web app and the dashboard JSON (`ortg_rk`, `pm_pg`). The Python side writes plain SQL with the same names the web reads.
- Trade-off: TypeScript code reads `row.ortg_rk` instead of camelCase. Accepted on purpose.

### postgres.js driver (`postgres` package) for the web app
- Why: works the same against local Postgres and Neon's pooled connection string; no HTTP-only driver that would break local development.
- Trade-off: on Vercel each function instance holds a TCP connection; we cap the pool at a few connections and use Neon's `-pooler` host.

### Python 3.11+ pipeline (`nba_pipeline`) with pandas, pyarrow, psycopg 3, httpx
- Why: the working engine is pandas code. Porting it as-is keeps the math identical, and the golden files from the old engine are the parity target.
- Trade-off: two languages in one repo. The boundary is the database schema and the dashboard JSON shapes, both covered by tests.

### D3 for charts, drawn as custom SVG React components (no chart library)
- Why: the graphics are the product (posts and videos), so every pixel is ours: fonts, team colors, annotations. D3 is used for scales, shapes and ticks; React renders the SVG.
- Trade-off: more code per chart than a chart library.

### Fonts from @fontsource packages
- Why: `next/font/google` downloads fonts at build time, which fails without network access (and in some CI setups). Fontsource ships the font files in npm, so builds are offline and the studio PNG export can embed the same files.
- Trade-off: font versions update through npm, not automatically.

### Tailwind CSS v4 for layout utilities, CSS variables for the design tokens
- Why: fast responsive layout; colors, type scale and team accents live in CSS variables so the studio frames and pages share one look.

### Hosting target (documented only, not deployed): Neon + Vercel + GitHub Actions, $0/month
- Why: Neon free tier (0.5 GB) holds several seasons of box scores; Vercel Hobby runs the Next app; a GitHub Actions cron runs the pipeline once a day for free on a public repo (2,000 free minutes a month on a private one).
- Trade-off: Neon free compute suspends after inactivity, so the first page view after a quiet stretch takes about a second longer. Details in `docs/DEPLOY.md`.

## Database

### One schema file, SQL migrations generated by drizzle-kit, applied by either Node or Python
- Why: `web/src/db/schema.ts` is the only place tables are defined. `python -m nba_pipeline migrate` applies the same `web/drizzle/*.sql` files and writes the same `drizzle.__drizzle_migrations` rows (same sha256 hash and timestamp) as `drizzle-kit migrate`, so the daily GitHub Action needs no Node install and either tool can be used on any database.
- Trade-off: the Python migrator mirrors drizzle-orm's rules (apply entries newer than the last recorded `created_at`, statements split on `--> statement-breakpoint`). If drizzle changes its journal format, update `pipeline/nba_pipeline/db.py`.

### Stats stored at display precision
- Why: the original engine rounded at output (one decimal; gap z-scores to two). Storing the same values makes exports byte-for-byte comparable with its golden JSON, and the web shows exactly what the old dashboard showed.
- Trade-off: re-aggregating stored per-game rates loses precision; aggregates are always recomputed from counting stats in the pipeline, never from stored rates.

### Season tables are rebuilt on every run; facts are upserted; snapshots are replaced per date
- Why: ranks, gap z-scores (which use the season's spread of gaps) and pre-game averages change whenever a game is added, so `team_season`, `player_season`, `game_gaps` and `player_game_deltas` are recomputed for the whole season in one transaction. Box scores and schedule rows are facts and are upserted by key. Injuries, odds and editorial are dated snapshots: a run replaces that date's rows.
- Trade-off: `team_season` and `player_season` hold only the latest run (as the spec asks); a past date shows today's season numbers. `as_of` on those rows says which run produced them.

### Player ids are bigint
- Why: the engine gives patch-file players without an ESPN id a crc32 id, which can exceed a 32-bit integer.

## Pipeline

### Port the engine line by line, then widen it to every game
- Why: the golden files are the contract. `compute.py` keeps the engine's formulas, rounding and pandas operations (even its sort calls, so tie order matches), then runs the same per-game code for every game of the season instead of only last night: box order, deltas and flags, team-vs-team gaps, rest, records entering, upsets.
- Trade-off: a full-season run recomputes everything (about 3 seconds for the fixture day, roughly 10 to 20 seconds late in a season).

### A run for date D counts only games before D
- Why: makes `--date` backfills reproduce that morning; on a normal morning it changes nothing (tonight's games are not final yet).
- Trade-off: none for daily use. The engine counted whatever the files held.

### export-json and digest read the database, through the same code as the parity test
- Why: `dashboard_files(tables)` is the only code that builds the old dashboard's ten files. The parity test feeds it rows from memory and rows read back from Postgres, so the database is proven to hold everything the dashboard needs.
- Trade-off: ordering rules the engine inherited from hoopR's file order are written out explicitly in `export.py` (games by tip, results by tip descending then ESPN id, and so on).

### Win odds from ESPN's predictor, else the no-vig moneyline split
- Why: the old task got win odds from Sportradar through a Claude tool that a GitHub Action cannot call. ESPN's summary carries a predictor before tip-off and the DraftKings moneylines; both are free and come with the line. `odds.wp_source` records which one was used.
- Trade-off: numbers will differ slightly from Sportradar's. `odds.json` in `--inputs` still overrides.

### Injuries from ESPN's injuries JSON, with the old task's status rules in code
- Why: the old task read ESPN's injuries web page with an LLM. The JSON endpoint gives the same data with structure; game-day designations are read from the comment text, notes are built from structured fields (never ESPN's prose), and names are normalized to the box-score spelling when exactly one player matches.
- Trade-off: the parser was written against a synthetic sample (ESPN is blocked in the build sandbox). `record-fixtures` saves a real response for a follow-up test.

### Editorial is a provider interface with a no-op default
- Why: v1 has no AI-written notes. `NoopEditorial` writes nothing, `FileEditorial` reads `editorial.json`, and a `ClaudeEditorial` TODO describes the Claude API version (digest in, JSON out). The web app falls back to data: a factual lede and "best matchups by net rating".
- Trade-off: without a provider the brief check ("two date rows and one headline") is a warning, not an error.

### Unattended checks: "30 teams" is a warning
- Why: the engine's finish step treated fewer than 30 teams as an error, which would fail the daily job on opening night. Everything else (period sums, player points versus team points, injury rows for teams not playing, bad statuses, duplicates) stays an error and marks the run as `error` in `pipeline_runs` (the data still loads; the job exits non-zero).

### Only games between two NBA teams; NBA Cup placeholders skipped
- Why: a dry run on the full 2025-26 season found ESPN's All-Star games (World, Stars, Stripes) filed as regular season, which would add three fake teams to the ranks and break the team foreign keys, plus placeholder player rows with no athlete. Both are dropped and counted in the run meta. NBA Cup knockout games list `TBD` teams until the matchups are set; they load normally once ESPN fills in the teams.
- Known gap: the NBA Cup championship game is in hoopR's regular-season files but does not count in the official standings; v1 counts it, like the engine did.

### Daily schedule: two cron entries, idempotent run
- Why: GitHub cron is UTC and the season spans both EDT and EST. 13:45 and 14:45 UTC give 9:45 a.m. New York time in either; the extra run is a free refresh.

### Points off turnovers are the opponent's ESPN figure (golden files regenerated)
- Why: ESPN's team stat `turnoverPoints` is labeled "Points Conceded Off Turnovers": the points the opponent scored off this team's turnovers. The original engine stored it as points the team scored, so a team that threw the ball away looked good. `compute.py` now swaps it per game: `pts_off_to` is the opponent's figure (points scored off the opponent's turnovers), and the team's own figure is the points it allowed (`opp_pts_off_to_pg`). The mirror rows and PATCH files keep ESPN's number as is.
- Check: on 2026-11-02 Charlotte committed 27 turnovers against Detroit. ESPN gives Charlotte 37 and Detroit 9, so we now show Detroit 37 and Charlotte 9. Without trusting any label, the stored figure now follows the other team's turnovers (r = 0.74 over the fixture season), not the team's own (r = 0.19). `tests/test_points_off_turnovers.py` holds these checks. Before and after, on the game page and the recap graphic: `docs/screenshots/fix-points-off-turnovers.png`.
- Golden files: regenerated with `cd pipeline && python3 -I tests/regen_golden.py`. Only these fields changed: `pts_off_to` in `box_teams`, the four points off turnovers rows in `box_compare` (the two sides swap and the edge flips; z, gap and level stay the same), and `pts_off_to_pg`, `opp_pts_off_to_pg` and their ranks in `team_season`. The other seven files and `digest.txt` are byte for byte the same.
- Trade-off: the golden files are now the original engine's output plus this fix, and `docs/reference/nba_build.py` keeps the old reading for the record. Stored data needs no migration: every run upserts all of the season's `team_games` rows and rebuilds `team_season` and `game_gaps`, so the next run corrects them.

### A player played when ESPN says so, even at 0 minutes (golden files regenerated)
- Why: ESPN rounds minutes to whole numbers, so a player on the floor for under 30 seconds shows 0 minutes but `did_not_play` is false. The original engine used `minutes > 0` as "played", which left those games out of `player_season` (games played and totals) and of the pre-game averages in `player_game_deltas`, marked them `dnp` in export-json, and listed the player with those who did not play. The check "player points do not add up to the team score" sums only non-dnp players, so one of these players scoring a basket would have failed the daily run. Now `did_not_play` alone decides, in `compute.py`, `export.py`, `stories.py`, `audit.py` and the web app.
- Box score: these players sit at the end of the bench list with "0" in the minutes column and their full line, like any other player. The "Did not play" note lists only players ESPN marks as not playing.
- Check: the fixture season has 8 such player-games (for example LJ Cryer, GSW, game 401909285: 0 minutes, 1 assist, +2). `test_zero_minute_players` in `pipeline/tests/test_stats.py` checks that every player's games played equals his games with `did_not_play` false, that these 8 have pre-game delta rows, and that LJ Cryer sits last on the Warriors' bench.
- Golden files: regenerated with `cd pipeline && python3 -I tests/regen_golden.py`. Only `player_season.json` (games played and every per-game and percentage field for the players with such games, plus the order of rows on their teams) and the pre-game average and delta fields of 3 rows in `box_players.json` changed. The other nine files and `digest.txt` are byte for byte the same.
- Trade-off: a player's minutes per game drop a little, since a 0-minute game now counts as a game. Stored data needs no migration: every run rebuilds `player_season`, `player_game_deltas` and `stories` for the season.

### The 3-day look-ahead is a dated snapshot table (`game_previews`)
- Why: tomorrow's matchup must be complete before the next run, so each run stores, for its date and the two days after, the records, rest, back-to-backs and missing scoring it saw, with the date of the injury report behind them. The web shows a future date from the newest run's rows, so the numbers on screen are the ones the checks verified.
- Trade-off: records and season ranks for the day after tomorrow do not yet include tomorrow's results. The page says what date the numbers run through.

### Rest after tonight from the schedule, up to tonight from games played
- Why: a back-to-back must show before either game is played, which only the schedule can tell. Tonight and earlier keep the engine's rule (games played), so the golden files do not change; a warning fires if the two disagree for tonight, which means a game before tonight is missing.

### Odds and injuries for 3 days in the daily job
- Why: lines often post a day or two before tip. Fetching every game in the window costs about 20 to 45 ESPN requests a run, one at a time. The dashboard's `injuries.json` keeps tonight's teams only, so the old shapes do not change.

### Shots: one row per attempt, rewritten only for games whose shots changed
- Why: the charts need every attempt's spot. A season has about 220,000 attempts, about 45 MB with indexes, which fits Neon's free plan, but rewriting all of them every morning would churn the database for nothing. `shot_games` keeps a hash of each game's rows, and a run deletes and copies in (with COPY) only the games whose hash changed. Zone profiles are small and rebuilt every run, like `team_season`.
- Trade-off: a game whose shots disappear from the source keeps its old rows, the same as box scores (a run never deletes facts it no longer sees). The shot file is optional: when it is missing or unreadable the run warns and leaves every shot table as it was.

### Three or two: makes by their points, misses by the line
- Why: the shot file gives a miss 0 points, so only its spot can say whether it was a three. A make's points are certain, so they decide. The line agrees with them on 99.96% of 2025-26 makes anyway, and this way made threes and points from shots match the box score exactly.
- Trade-off: right at the line, makes and misses follow slightly different rules (42 of 103,346 makes in 2025-26 would change sides).

### Missed heaves are not attempts
- Why: since 2025-26 the box score does not count a missed end-of-quarter heave as a field goal attempt, and ESPN types them "Heave Jump Shot". Keeping them would add 85 attempts on the fixture day that no box score has.
- Trade-off: the backcourt zone keeps only made heaves and the rare long shot that does count, so its FG% means little. Pages show it only when there are attempts.

### Zone profiles carry the league's numbers on every row
- Why: every zone table compares with the league. Storing the league's FG%, points per shot and share beside each row, plus the gap between the two printed FG% values, keeps that math in Python, where tests cover it; the web only prints.
- Trade-off: the league numbers are repeated on every row (a few thousand rows a season).

## Play-by-play

### Read the play-by-play every run, store only what is computed from it
- Why: the season file is about 600,000 plays (20 MB as parquet), and Neon's free plan is 1 GB. The run downloads it, rebuilds who was on the floor, and keeps seven small tables (19 MB for a full season, measured on 2025-26). The worm chart is one row per game with three arrays (time, road score, home score) instead of a row per basket.
- Trade-off: a new question about plays (a stat the tables do not hold) means a pipeline change and a rerun, not a SQL query. Every run rebuilds the season's play-by-play tables, about 25 seconds late in a season.

### Plays in game_play_number order
- Why: `sequence_number` is ESPN's edit order; a play corrected later gets a high number and sorts after plays that followed it. `game_play_number` follows the game clock, and in it the running score is consistent on every row.
- Trade-off: within one clock time, an edited row can still land a play or two late (a substitution after the free throws it came before). The lineup rebuild absorbs most of these; the rest show up in the plus-minus check.

### Rebuild lineups by reading each team-period the most consistent way
- Why: the feed never lists period starters, and ESPN's substitution rows are sometimes wrong (both the original and the corrected row kept, the wrong player named leaving, nobody named). A plain "first appearance" rule failed on 5 of the first 107 games this season. Scoring candidate readings by contradictions (rows that cannot apply, dropped rows, plays naming a benched player) fixes them; box-score minutes only break exact ties. On 2025-26, 26,597 of 26,599 player-games come within a minute of the box score.
- Trade-off: a substitution ESPN never logged leaves no trace to repair. Those games are reported by the minutes check (one this season so far, one all of last season), and their lineups are kept as the feed tells them.

### Free throws count for the lineup on the floor at the foul
- Why: that is how the box score's plus-minus is kept. Crediting the lineup at the shot matched it in about 4 player-games in 10 on 2025-26; crediting the lineup at the foul matches 98.8%, which makes plus-minus a working check on the rebuild.
- Trade-off: a stretch can be credited free throws taken after it ended. Its seconds stay correct; only the points move.

### Lineup possessions use the app's estimate, per stretch of play
- Why: FGA - OREB + TOV + 0.44 x FTA, averaged for both teams, is how the team ratings count possessions, so a lineup's net rating reads on the same scale as its team's. Summed over a game, the stretches land within 1 possession of the box score's figure on the fixture day. Missed heaves are left out of attempts because ESPN's box score leaves them out.
- Trade-off: it is an estimate; counting possessions play by play would differ slightly, most in short stretches. Lineups show only with 50 possessions or more.

### "Off the floor" means his team's time without him in the games he played
- Why: it compares like with like (same opponents, same nights) and does not charge a player for games he missed.
- Trade-off: a player who plays almost every minute has a small off sample; the tables show minutes and grey out fewer than 50 possessions.

### Clutch time is a state of the game clock and the score
- Why: the usual definition (last 5 minutes of the 4th or overtime, margin within 5). A play counts when the margin before it is within 5, so the basket that stretches a 5-point game to 7 is clutch; clutch minutes are the stretches of clock in that state.
- Trade-off: early in a season the samples are a few minutes a team; every figure is shown with its games and minutes.

### The play-by-play step stands apart from the engine
- Why: it runs after the box-score engine's checks and cannot change the golden files. A missing file leaves the play-by-play tables as they were; a failure is recorded and the box scores still load. Its messages start with "play-by-play:", and the parity test checks only the engine's own warnings (the play-by-play tests pin the one known gap on the fixture day).
- Trade-off: two sets of checks to read in `pipeline_runs`.

## Power ratings and the model

### Ridge regression on game efficiency, refit for every date
- Why: opponent adjustment needs every team's schedule at once, and a ridge penalty gives the early-season shrinkage toward average for free. Fitting each date from the games before it gives the ratings history for the chart and the pregame ratings for the backtest in one pass, and makes look-ahead impossible by construction.
- Trade-off: the season tables are rebuilt every run (under a second). The weights (7 games for teams, 100 for home court and the spread of results) are fixed in code, chosen on last season.

### Home court and the spread of results start from typical values
- Why: the task asks for about 2 and 12 points to start and to learn from this season. Both are prior-weighted averages: home court inside the regression, the spread from earlier games' misses.
- Trade-off: with a weight of 100 games, early-season numbers lean on the priors on purpose.

### ESPN's line for the backtest comes from the play-by-play
- Why: our `odds` table only has the lines the daily job saw, from the day it started running. The play-by-play has ESPN's pregame spread for every game of the season. Upcoming games use the run's odds.
- Trade-off: we do not know when ESPN took the spread (open or close). It is labeled "pregame".

### Every prediction is stored, not just the backtest summary
- Why: the Model page lists each game, and the game page shows the model's line and how it built it. One row per game is small.

## Web

### Any date this season, measured from the newest run
- Why: the newest run is the data's "today". Before it, a date shows final scores linking to each game page; from it and two days on, the full matchup breakdown; after that, the schedule. The date picker is a plain GET form (`?date=YYYY-MM-DD`), so it needs no client JavaScript and the URL stays shareable.

### Pages render per request; the default date follows the data
- Why: `/` shows today in New York, unless the newest pipeline run is more than three days old (the seeded demo, the off-season), in which case it shows that run's date with a note. Any page takes `?date=`.

### Charts are server-rendered SVG with native tooltips and a table twin
- Why: no client JavaScript for charts on regular pages; every chart has its numbers in a table nearby (the line score under the quarter flow, the ratings table beside the scatter). Wide charts render a second, narrower version for phones instead of shrinking text.

### The game flow chart replaces the quarter chart when a game has play-by-play
- Why: the margin after every basket shows everything the margin after each quarter does, and more; two flow charts on one page would repeat each other. The line score stays under it, scoring runs get their own table, and games without play-by-play keep the quarter chart. The studio's game recap keeps the quarter chart; the new Game flow template carries the full worm.

### Broadcast type for scores and big numbers
- Why: the brief asks for a broadcast look, so scores and studio numbers use Big Shoulders Display (a condensed face drawn from Chicago signage); tables and labels use Archivo with tabular figures.
- Trade-off: this departs from the generic dashboard advice to keep hero numbers in the text face.

### Studio frames are pure components, exported with html-to-image at pixel ratio 1
- Why: the editor preview, the full-size `/studio/frame` route and the PNG all render the same component, so what you see is what you post, at exactly 1080x1350, 1080x1920 or 1920x1080. Fonts come from the same origin, so the export embeds them.
- Trade-off: html-to-image re-renders through an SVG foreignObject; exotic CSS (filters, backdrop blur) is avoided in frames.

### Site pages live in a `(site)` route group, frames in `(bare)`
- Why: `/studio/frame` must render with no header or footer for screenshots and headless exports; route groups keep URLs unchanged.

### Shot charts: basket at the top, hexes colored by their zone
- Why: a half court drawn to NBA dimensions with the basket at the top reads like NBA.com's charts. The hexbin view sizes each hex by attempts and colors it by the subject's FG% from the zone most of its shots came from, against the league: the same number as the zone table's +/- column, gray under 5 attempts. Coloring each hex by its own handful of shots flipped neighbors between blue and orange on a team's first seven games, which is noise, not a hot spot.
- Trade-off: six zones are coarse, so a hot left wing and a cold right wing share one color. The makes and misses view shows every shot as it happened.

### Above the league is blue, below is orange
- Why: the site's validated diverging pair is plus blue and minus orange, and the zone table's +/- bars use it, so the hexes do too. The view is called "Against the league" rather than "Hot and cold", since hot usually means red.
- Trade-off: on a team's defense chart, blue means opponents shoot well against them. The panel says so.

### Game and team pages compare two sides in one zone table
- Why: two narrow tables (one per team, or offense and defense) hid their last columns in half-width panels. One table below both charts puts each side's made and attempted, FG%, gap, points per shot and share next to the league's.

### Shot chart math is tested with plain `node --test`
- Why: zone counts, hex binning, colors and tooltip text live in `web/src/lib/shots.ts` with no imports. Node 22 runs TypeScript files directly (type stripping), so the tests need no framework. `npm test` runs them, and CI runs it too.
- Trade-off: the test file imports `./shots.ts` with its extension, so `tsconfig.json` sets `allowImportingTsExtensions` (fine with `noEmit`).

### The studio shot chart covers last night only
- Why: the studio loads every graphic's data for the date up front. A season of shots for every player and team from last night would be hundreds of thousands of rows late in the season; last night's shots are about 3,000. Season charts live on the player and team pages.

### The studio handle comes from `NEXT_PUBLIC_BRAND_HANDLE`
- Why: set it once in `.env` or on Vercel; each graphic can still override it, and the URL keeps the current choice. No browser storage needed.

## Story finder

### Stories are rebuilt for every night, every run
- Why: any night can be browsed, a late box-score fix flows into old stories, and the no-look-ahead rule is easy to test (a run as of an earlier date gives the same stories for the nights it covers). It takes under a second and about 20 rows a night (3,400 a season).
- Trade-off: a story can change after the fact when ESPN corrects a box score.

### Rarity is a z-score for every kind
- Why: outliers come with a z; streaks, firsts and rare lines come with a probability, turned into the z with the same tail. One scale lets one ranking mix them. Prominence (minutes and usage) scales it by 0.5 to 1.5, so a role player's career night can still beat a star's ordinary big game, but not by much.
- Trade-off: the probabilities are simple models (a streak treats games as independent; league rates early in a season rest on a few hundred games). The numbers behind each score are stored, and the card shows them.

### The spread behind an outlier has a floor
- Why: early in a season a player's spread over 4 or 5 games can be tiny, and a sample standard deviation of 1 point makes a 6-point swing look like a 6-sigma night. The floors (points 4, rebounds 2, assists 1.5, threes 1, plus-minus 6, true shooting 8) are about a third to half of a typical rotation player's full-season spread.
- Trade-off: a very steady player's real outliers are understated until his own spread passes the floor.

### One story per player per night
- Why: a 45-point, 15-rebound, 8-three night set off five stories that crowded out the rest of the slate. The best one leads and the others show as "Also that night".
- Trade-off: the second story of a big night cannot rank on its own.

### Team swings compare the last stretch with the games before it
- Why: comparing the last 10 with a season that includes them waters the gap down. Early on the window is half the team's games, so a turnaround shows by the 6th game.
- Trade-off: before 20 games the window is short and noisy, so the bar (z of 2) is rarely reached; none of the fixture day's swings make it.

### The studio's Story card covers last night
- Why: like the other templates, the studio loads one date. Every story card on the Stories page links to the studio with the next morning's date, so any story of the season can become a graphic.

## Versions and environment notes

### Next.js 16.4, React 19.3, TypeScript 5.9, ESLint 9
- Why: current stable Next and React. TypeScript 7 (the native port) and ESLint 10 were the npm defaults at build time, but Next's build-time type check and `eslint-config-next`'s plugins are proven on TypeScript 5.x and ESLint 9; npm prints a deprecation note for ESLint 9.
- Note: `next dev` writes `web/AGENTS.md` (agent notes from the Next.js team). It is committed so the working tree stays clean.

### Smoke test uses the machine's Playwright, not a project dependency
- Why: browsers are large and machine-specific. `web/scripts/smoke.mjs` loads `playwright` from the global install (`npm i -g playwright && npx playwright install chromium`), and CI installs it the same way.

### Built in a sandbox without Docker, ESPN or Google Fonts
- Postgres 16 ran from local binaries; `docker-compose.yml` uses the official `postgres:16` image and was not run here.
- ESPN parsers are tested against saved and synthetic responses only; the first live run is the real test of `fetch_summary` and `fetch_injuries`.
