# Decisions

Short entries: the decision, why, and the trade-off. Newest at the bottom of each section.

## Stack

### Next.js App Router + TypeScript + React for the web app
- Why: server components can query Postgres directly, so pages need no API layer; Chops already works in Next/TS.
- Trade-off: pages render per request (`dynamic = "force-dynamic"`) so `next build` never needs a database. Each visit hits Postgres; fine at this traffic, and data only changes once a day.

### Drizzle ORM + drizzle-kit, not Prisma
- Why: the schema lives in one TypeScript file (`web/src/db/schema.ts`) and drizzle-kit generates plain SQL migrations (`web/drizzle/*.sql`) that the Python pipeline can read and apply. Prisma's engines download from binaries.prisma.sh, which the build sandbox could not reach, and its generated client adds a binary to every deploy.
- Trade-off: fewer guard rails than Prisma (no generated client with relation helpers); queries are written with the Drizzle query builder or `sql` templates.

### snake_case everywhere (SQL columns, Drizzle keys, Python, JSON)
- Why: one vocabulary across the pipeline, the database, the web app and the dashboard JSON (`ortg_rk`, `pm_pg`). The Python side writes plain SQL with the same names the web reads.
- Trade-off: TypeScript code reads `row.ortg_rk` instead of camelCase. Accepted on purpose.

### postgres.js driver (`postgres` package) for the web app
- Why: works the same against local Postgres and Neon's pooled connection string; no HTTP-only driver that would break local development.
- Trade-off: on Vercel each function instance holds a TCP connection; we cap the pool at a few connections and use Neon's `-pooler` host.

### Python 3.11+ pipeline (`nba_pipeline`) with pandas, pyarrow, psycopg 3, httpx
- Why: the working engine is pandas code. Porting it as-is keeps the math identical, and the golden files from the old engine are the parity target.
- Trade-off: two languages in one repo. The boundary is the database schema and the dashboard JSON shapes, both covered by tests.

### D3 for charts, drawn as custom SVG React components (no chart library)
- Why: the graphics are the product (posts and videos), so every pixel is ours: fonts, team colors, annotations. D3 is used for scales, shapes and ticks; React renders the SVG.
- Trade-off: more code per chart than a chart library.

### Fonts from @fontsource packages
- Why: `next/font/google` downloads fonts at build time, which fails without network access (and in some CI setups). Fontsource ships the font files in npm, so builds are offline and the studio PNG export can embed the same files.
- Trade-off: font versions update through npm, not automatically.

### Tailwind CSS v4 for layout utilities, CSS variables for the design tokens
- Why: fast responsive layout; colors, type scale and team accents live in CSS variables so the studio frames and pages share one look.

### Hosting target (documented only, not deployed): Neon + Vercel + GitHub Actions, $0/month
- Why: Neon free tier (0.5 GB) holds several seasons of box scores; Vercel Hobby runs the Next app; a GitHub Actions cron runs the pipeline once a day for free on a public repo (2,000 free minutes a month on a private one).
- Trade-off: Neon free compute suspends after inactivity, so the first page view after a quiet stretch takes about a second longer. Details in `docs/DEPLOY.md`.

## Database

### One schema file, SQL migrations generated by drizzle-kit, applied by either Node or Python
- Why: `web/src/db/schema.ts` is the only place tables are defined. `python -m nba_pipeline migrate` applies the same `web/drizzle/*.sql` files and writes the same `drizzle.__drizzle_migrations` rows (same sha256 hash and timestamp) as `drizzle-kit migrate`, so the daily GitHub Action needs no Node install and either tool can be used on any database.
- Trade-off: the Python migrator mirrors drizzle-orm's rules (apply entries newer than the last recorded `created_at`, statements split on `--> statement-breakpoint`). If drizzle changes its journal format, update `pipeline/nba_pipeline/db.py`.

### Stats stored at display precision
- Why: the original engine rounded at output (one decimal; gap z-scores to two). Storing the same values makes exports byte-for-byte comparable with its golden JSON, and the web shows exactly what the old dashboard showed.
- Trade-off: re-aggregating stored per-game rates loses precision; aggregates are always recomputed from counting stats in the pipeline, never from stored rates.

### Season tables are rebuilt on every run; facts are upserted; snapshots are replaced per date
- Why: ranks, gap z-scores (which use the season's spread of gaps) and pre-game averages change whenever a game is added, so `team_season`, `player_season`, `game_gaps` and `player_game_deltas` are recomputed for the whole season in one transaction. Box scores and schedule rows are facts and are upserted by key. Injuries, odds and editorial are dated snapshots: a run replaces that date's rows.
- Trade-off: `team_season` and `player_season` hold only the latest run (as the spec asks); a past date shows today's season numbers. `as_of` on those rows says which run produced them.

### Player ids are bigint
- Why: the engine gives patch-file players without an ESPN id a crc32 id, which can exceed a 32-bit integer.

## Pipeline

### Port the engine line by line, then widen it to every game
- Why: the golden files are the contract. `compute.py` keeps the engine's formulas, rounding and pandas operations (even its sort calls, so tie order matches), then runs the same per-game code for every game of the season instead of only last night: box order, deltas and flags, team-vs-team gaps, rest, records entering, upsets.
- Trade-off: a full-season run recomputes everything (about 3 seconds for the fixture day, roughly 10 to 20 seconds late in a season).

### A run for date D counts only games before D
- Why: makes `--date` backfills reproduce that morning; on a normal morning it changes nothing (tonight's games are not final yet).
- Trade-off: none for daily use. The engine counted whatever the files held.

### export-json and digest read the database, through the same code as the parity test
- Why: `dashboard_files(tables)` is the only code that builds the old dashboard's ten files. The parity test feeds it rows from memory and rows read back from Postgres, so the database is proven to hold everything the dashboard needs.
- Trade-off: ordering rules the engine inherited from hoopR's file order are written out explicitly in `export.py` (games by tip, results by tip descending then ESPN id, and so on).

### Win odds from ESPN's predictor, else the no-vig moneyline split
- Why: the old task got win odds from Sportradar through a Claude tool that a GitHub Action cannot call. ESPN's summary carries a predictor before tip-off and the DraftKings moneylines; both are free and come with the line. `odds.wp_source` records which one was used.
- Trade-off: numbers will differ slightly from Sportradar's. `odds.json` in `--inputs` still overrides.

### Injuries from ESPN's injuries JSON, with the old task's status rules in code
- Why: the old task read ESPN's injuries web page with an LLM. The JSON endpoint gives the same data with structure; game-day designations are read from the comment text, notes are built from structured fields (never ESPN's prose), and names are normalized to the box-score spelling when exactly one player matches.
- Trade-off: the parser was written against a synthetic sample (ESPN is blocked in the build sandbox). `record-fixtures` saves a real response for a follow-up test.

### Editorial is a provider interface with a no-op default
- Why: v1 has no AI-written notes. `NoopEditorial` writes nothing, `FileEditorial` reads `editorial.json`, and a `ClaudeEditorial` TODO describes the Claude API version (digest in, JSON out). The web app falls back to data: a factual lede and "best matchups by net rating".
- Trade-off: without a provider the brief check ("two date rows and one headline") is a warning, not an error.

### Unattended checks: "30 teams" is a warning
- Why: the engine's finish step treated fewer than 30 teams as an error, which would fail the daily job on opening night. Everything else (period sums, player points versus team points, injury rows for teams not playing, bad statuses, duplicates) stays an error and marks the run as `error` in `pipeline_runs` (the data still loads; the job exits non-zero).

### Only games between two NBA teams; NBA Cup placeholders skipped
- Why: a dry run on the full 2025-26 season found ESPN's All-Star games (World, Stars, Stripes) filed as regular season, which would add three fake teams to the ranks and break the team foreign keys, plus placeholder player rows with no athlete. Both are dropped and counted in the run meta. NBA Cup knockout games list `TBD` teams until the matchups are set; they load normally once ESPN fills in the teams.
- Known gap: the NBA Cup championship game is in hoopR's regular-season files but does not count in the official standings; v1 counts it, like the engine did.

### Daily schedule: two cron entries, idempotent run
- Why: GitHub cron is UTC and the season spans both EDT and EST. 13:45 and 14:45 UTC give 9:45 a.m. New York time in either; the extra run is a free refresh.

### Points off turnovers are the opponent's ESPN figure (golden files regenerated)
- Why: ESPN's team stat `turnoverPoints` is labeled "Points Conceded Off Turnovers": the points the opponent scored off this team's turnovers. The original engine stored it as points the team scored, so a team that threw the ball away looked good. `compute.py` now swaps it per game: `pts_off_to` is the opponent's figure (points scored off the opponent's turnovers), and the team's own figure is the points it allowed (`opp_pts_off_to_pg`). The mirror rows and PATCH files keep ESPN's number as is.
- Check: on 2026-11-02 Charlotte committed 27 turnovers against Detroit. ESPN gives Charlotte 37 and Detroit 9, so we now show Detroit 37 and Charlotte 9. Without trusting any label, the stored figure now follows the other team's turnovers (r = 0.74 over the fixture season), not the team's own (r = 0.19). `tests/test_points_off_turnovers.py` holds these checks. Before and after, on the game page and the recap graphic: `docs/screenshots/fix-points-off-turnovers.png`.
- Golden files: regenerated with `cd pipeline && python3 -I tests/regen_golden.py`. Only these fields changed: `pts_off_to` in `box_teams`, the four points off turnovers rows in `box_compare` (the two sides swap and the edge flips; z, gap and level stay the same), and `pts_off_to_pg`, `opp_pts_off_to_pg` and their ranks in `team_season`. The other seven files and `digest.txt` are byte for byte the same.
- Trade-off: the golden files are now the original engine's output plus this fix, and `docs/reference/nba_build.py` keeps the old reading for the record. Stored data needs no migration: every run upserts all of the season's `team_games` rows and rebuilds `team_season` and `game_gaps`, so the next run corrects them.

## Web

### Pages render per request; the default date follows the data
- Why: `/` shows today in New York, unless the newest pipeline run is more than three days old (the seeded demo, the off-season), in which case it shows that run's date with a note. Any page takes `?date=`.

### Charts are server-rendered SVG with native tooltips and a table twin
- Why: no client JavaScript for charts on regular pages; every chart has its numbers in a table nearby (the line score under the quarter flow, the ratings table beside the scatter). Wide charts render a second, narrower version for phones instead of shrinking text.

### Broadcast type for scores and big numbers
- Why: the brief asks for a broadcast look, so scores and studio numbers use Big Shoulders Display (a condensed face drawn from Chicago signage); tables and labels use Archivo with tabular figures.
- Trade-off: this departs from the generic dashboard advice to keep hero numbers in the text face.

### Studio frames are pure components, exported with html-to-image at pixel ratio 1
- Why: the editor preview, the full-size `/studio/frame` route and the PNG all render the same component, so what you see is what you post, at exactly 1080x1350, 1080x1920 or 1920x1080. Fonts come from the same origin, so the export embeds them.
- Trade-off: html-to-image re-renders through an SVG foreignObject; exotic CSS (filters, backdrop blur) is avoided in frames.

### Site pages live in a `(site)` route group, frames in `(bare)`
- Why: `/studio/frame` must render with no header or footer for screenshots and headless exports; route groups keep URLs unchanged.

### The studio handle comes from `NEXT_PUBLIC_BRAND_HANDLE`
- Why: set it once in `.env` or on Vercel; each graphic can still override it, and the URL keeps the current choice. No browser storage needed.

## Versions and environment notes

### Next.js 16.4, React 19.3, TypeScript 5.9, ESLint 9
- Why: current stable Next and React. TypeScript 7 (the native port) and ESLint 10 were the npm defaults at build time, but Next's build-time type check and `eslint-config-next`'s plugins are proven on TypeScript 5.x and ESLint 9; npm prints a deprecation note for ESLint 9.
- Note: `next dev` writes `web/AGENTS.md` (agent notes from the Next.js team). It is committed so the working tree stays clean.

### Smoke test uses the machine's Playwright, not a project dependency
- Why: browsers are large and machine-specific. `web/scripts/smoke.mjs` loads `playwright` from the global install (`npm i -g playwright && npx playwright install chromium`), and CI installs it the same way.

### Built in a sandbox without Docker, ESPN or Google Fonts
- Postgres 16 ran from local binaries; `docker-compose.yml` uses the official `postgres:16` image and was not run here.
- ESPN parsers are tested against saved and synthetic responses only; the first live run is the real test of `fetch_summary` and `fetch_injuries`.
